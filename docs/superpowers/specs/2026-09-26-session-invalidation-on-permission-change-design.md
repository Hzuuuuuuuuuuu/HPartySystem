# 权限变更后的会话失效设计

## 1. 背景与问题

登录时，`AuthService` 将用户角色、权限和数据范围组装到 `LoginUser`，并写入 Sa-Token 会话。后续 `@SaCheckPermission` 从会话中的权限集合判断访问权限。

当前用户角色、角色菜单、菜单状态/权限标识、账号状态或密码发生变化时，管理 Service 只更新数据库，不清理已有会话。因此旧会话会继续携带旧权限，表现为：

- 管理员已经调整权限，但用户仍使用旧权限；
- 菜单可能已经显示或隐藏与后端权限结果不一致；
- 访问 `develop:step:list` 等接口时偶发 403“没有操作权限”；
- 账号停用、删除或密码重置后，旧会话仍可能继续有效。

## 2. 目标与非目标

### 目标

1. 任何影响鉴权结果的管理操作成功提交后，立即使受影响用户的全部 Sa-Token 会话失效。
2. 用户下次登录时重新加载最新角色、权限和数据范围。
3. 事务回滚时不误清理会话。
4. 不新增数据库字段，不改变前端 API，不改变默认端口或登录协议。

### 非目标

- 不改为每个请求实时查询数据库权限。
- 不引入权限版本号或新的缓存协议。
- 不修改角色与菜单的业务授权规则。
- 不改变菜单显示逻辑和 `@SaCheckPermission` 的使用方式。

## 3. 方案

新增集中式 `SessionInvalidator`（名称可按现有命名最终调整），封装 Sa-Token 注销操作：

```java
void invalidateUser(Long userId);
void invalidateUsers(Collection<Long> userIds);
void invalidateUsersAfterCommit(Collection<Long> userIds);
```

其中 `invalidateUsersAfterCommit` 在存在 Spring 事务时注册 `afterCommit` 回调；无事务时直接执行。实际注销使用 `StpUtil.logout(userId)`，使该用户的全部设备会话失效。

各 Service 只负责收集受影响用户 ID，不直接散落调用 `StpUtil`。

## 4. 受影响操作

### 用户服务 `SysUserService`

- `updateUser`：清理被修改用户；无论是否同时修改角色，只要用户信息、状态、组织或角色发生变化均清理。
- `changeStatus`：清理目标用户。
- `removeUser`：清理目标用户。
- `resetPwd`：清理目标用户，确保密码重置后旧会话失效。
- `addUser`：新用户没有已有会话，不清理。

### 角色服务 `SysRoleService`

在变更前查询该角色关联的用户 ID，然后执行数据库操作，成功提交后清理这些用户：

- `updateRole`
- `assignMenus`
- `changeStatus`
- `removeRole`（虽然当前实现禁止删除仍被用户引用的角色，仍按统一边界处理）

角色名称、角色权限字符串、数据范围、状态、菜单关联任一变化都触发清理，因为它们都会影响登录会话中的角色、权限或数据范围。

### 菜单服务 `SysMenuService`

在修改或删除前查询拥有该菜单的角色对应的用户 ID，事务提交后清理：

- `updateMenu`：菜单权限标识、状态、可见性、路由路径等变化都可能影响菜单或鉴权结果，因此统一清理。
- `removeMenu`：先收集关联用户，再清理角色菜单关联并删除菜单。
- `addMenu`：新菜单尚未产生既有会话影响，不清理；后续角色授权通过角色服务触发清理。

## 5. Mapper 查询

在 `SysRelationMapper` 增加面向会话失效的只读查询，保持关联表无实体的现有设计：

- 按角色查询用户 ID；
- 按角色集合批量查询用户 ID；
- 按菜单查询角色 ID 或直接查询受影响用户 ID。

所有批量查询由 Service 在传入前保证集合非空，避免 MyBatis 动态 SQL 生成空 `IN ()`。查询结果去重后再提交给会话失效组件。

## 6. 事务与失败行为

- 会话失效回调只在事务成功提交后执行。
- 数据库更新失败或事务回滚时，原会话保持不变。
- Redis/Sa-Token 注销失败不得回滚已经成功提交的权限数据库更新；记录日志并由后续重新登录或运维处理恢复。
- 用户访问旧会话时，若会话已被注销，按现有未登录流程返回 401；前端已有统一跳转登录处理。

## 7. 验证

### 自动验证

- 编译 `hparty-server` 全模块。
- 运行受影响的系统模块测试；如果现有测试环境需要外部服务，记录实际失败原因，不将其伪称为通过。
- 运行 `hparty-web` 构建，确保无 API 或权限类型回归。
- `git diff --check`，确认没有冲突标记或空白错误。

### 手工验证

1. 使用有 `develop:step:list` 的账号登录，保留当前会话。
2. 管理员修改该用户角色，或移除该角色的流程配置菜单权限。
3. 使用原会话访问 `/api/develop/flow/steps`，确认会话失效并要求重新登录。
4. 重新登录，确认菜单和接口权限与最新授权一致。
5. 测试角色状态变更、账号停用、密码重置，同样确认旧会话失效。
6. 让一次权限更新事务失败，确认原会话没有被提前注销。

## 8. 风险与兼容性

- 权限调整会使受影响用户立即退出所有设备，这是预期的安全行为，应在管理端操作提示或操作日志中可追溯。
- 不涉及数据库结构和 Flyway 迁移。
- 不改变现有权限标识；`develop:step:list` 是否授予某角色仍由 `sys_role_menu` 决定。
- 批量角色或菜单变更可能使较多用户同时重新登录，但权限变更本身已经要求重新建立会话。
