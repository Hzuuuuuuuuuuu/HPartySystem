# 开发规范

> 写任何代码前请读完本文。这里的每一条都对应现有代码的实际写法，新代码应当长得和它们一样。

> `docs/03-数据库设计.md`（表结构与设计约定）

## 一、后端分层与包结构

模块依赖严格单向，**禁止反向依赖**：

```
hparty-admin  →  hparty-develop / hparty-party / hparty-system  →  hparty-framework  →  hparty-common
```

`hparty-party` **不依赖** `hparty-system`。跨域取数据（查组织名、人员姓名）用注解 SQL，
参照 `hparty-party/mapper/PartyLookupMapper.java`。这是有意为之 —— 避免 party 与 system 互相纠缠。

每个业务模块内的包结构：

```
com.hparty.<模块>/
├── controller/        REST 接口，只做参数接收与结果包装
├── service/           业务逻辑，直接写 @Service 具体类（不必 interface + impl 两件套）
├── mapper/            MyBatis-Plus Mapper，简单查询用 LambdaQueryWrapper，跨表用 @Select
├── domain/
│   ├── entity/        与表一一对应
│   ├── dto/           入参（XxxDTO / XxxQuery）
│   └── vo/            出参（XxxVO）
├── enums/             本模块的枚举
└── util/              本模块的工具类
```

## 二、统一返回体与错误码

所有接口返回 `com.hparty.common.core.R<T>`：

```java
R.ok()                    // 成功，无数据
R.ok(data)                // 成功，带数据
R.ok("提示信息", data)     // 成功，带自定义提示
R.fail("错误信息")         // 失败
R.fail(code, "错误信息")   // 失败，指定错误码
```

响应体结构：`{code, msg, data, timestamp}`

| 错误码 | 含义 | 什么时候用 |
|---|---|---|
| 200 | 成功 | |
| 400 | 参数校验失败 | `@Valid` 校验未通过，全局异常处理器自动转换 |
| 401 | 未登录 / 登录过期 | Sa-Token 抛出，自动转换 |
| 403 | 无操作权限 | `@SaCheckPermission` 未通过 |
| 500 | 系统内部错误 | 未预期的异常，兜底 |
| **600** | **业务处理失败** | **业务规则不满足，用 `BizException` 抛出** |
| **601** | **流程规则未通过** | 发展党员的 `DevRuleEngine` 校验失败 |

前端axios拦截器对 600 / 601 有区分处理：**601 用 warning 提示（可读性强、停留久），
600 用 error**。写业务异常时选对错误码。

### 抛异常

```java
throw new BizException("该人员已存在发展党员流程记录");            // 600
throw new BizException(ResultCode.FORBIDDEN, "无权操作该组织");   // 403
BizException.throwIf(condition, "提示信息");                      // 条件成立时抛
```

**不要**在 Service 里 `try-catch` 后返回 `R.fail()` —— 直接抛异常，全局处理器统一转。
`GlobalExceptionHandler` 已覆盖参数校验、鉴权、SQL 异常等常见情况。

## 三、数据权限（最容易出错的地方）

系统的数据权限分两层，**两层都要做，缺一不可**。

### 3.1 列表查询：追加 SQL 条件

```java
QueryWrapper<DevApplicant> wrapper = new QueryWrapper<>();
DataScopeHelper.apply(wrapper);                          // 默认 org_id / person_id
DataScopeHelper.apply(wrapper, "publish_org_id", null);  // 表里组织字段名不是 org_id 时
```

组织表用物化路径 `sys_dept.org_path`（形如 `/1/3/7/`），前缀匹配取整棵子树。
`data_scope` 的五个取值：1=全部 2=本级 3=本级及以下 4=仅本人 5=自定义。

### 3.2 按主键的详情/改/删：越权校验

**列表条件拦不住直接构造 ID 的请求。** 所有按主键的操作都必须显式校验：

```java
public AmTask get(Long taskId) {
    AmTask task = taskMapper.selectById(taskId);
    if (task == null) {
        throw new BizException("任务不存在");
    }
    if (!DataScopeHelper.canAccessOrg(task.getPublishOrgId())) {
        throw new BizException("无权操作其他党组织的任务");
    }
    return task;
}
```

`update` / `remove` / 子资源查询都先调 `get()`，天然覆盖。

### 3.3 创建时不要信任客户端传的组织 ID

```java
Long orgId = dto.getOrgId() != null ? dto.getOrgId() : SecurityUtils.getOrgId();
if (orgId == null) {
    throw new BizException("当前账号未分配所属党组织，无法创建。");  // 超管可能没有 org_id
}
if (!DataScopeHelper.canAccessOrg(orgId)) {
    throw new BizException("无权在指定党组织下创建");
}
```

### 3.4 容器类型说明

`DataScopeHelper` 的参数类型是 `AbstractWrapper`，因为 MyBatis-Plus 里
`QueryWrapper` 与 `LambdaQueryWrapper` 是**兄弟类**（都继承 `AbstractWrapper`），
彼此没有继承关系。不要试图把它改成 `QueryWrapper`。

## 四、实体与 Mapper

### 4.1 是否继承 BaseEntity —— 逐表核对

`com.hparty.common.core.BaseEntity` 提供 5 个字段：
`createBy` / `createTime` / `updateBy` / `updateTime` / `delFlag`（带 `@TableLogic`）。

**表中这 5 列齐全才能继承**，缺任意一列就改为 `implements Serializable` 并自行声明实际拥有的列。
写新实体时对照当前完整 DDL（V1 加后续 Flyway 迁移）逐列核对，**不要照抄别的实体**。

```java
// 继承（5 列齐全）
@Data
@EqualsAndHashCode(callSuper = true)
@TableName("dev_applicant")
public class DevApplicant extends BaseEntity {
    @TableId(value = "applicant_id", type = IdType.AUTO)
    private Long applicantId;
    // 不要再声明 createBy 等 5 个字段
}

// 不继承（缺列）
@Data
@TableName("dev_step_record")
public class DevStepRecord implements Serializable {
    @Serial
    private static final long serialVersionUID = 1L;

    @TableId(value = "record_id", type = IdType.AUTO)
    private Long recordId;

    @JsonFormat(pattern = "yyyy-MM-dd HH:mm:ss")
    @TableField(value = "create_time", fill = FieldFill.INSERT)
    private LocalDateTime createTime;
}
```

### 4.2 字段约定

- 主键：`@TableId(value = "列名", type = IdType.AUTO)`
- **非主键字段不加 `@TableField("xxx")`**，依赖 MyBatis-Plus 的驼峰转下划线
- 日期：`LocalDate` + `@JsonFormat(pattern = "yyyy-MM-dd")`
- 时间：`LocalDateTime` + `@JsonFormat(pattern = "yyyy-MM-dd HH:mm:ss")`
- 金额 / 比率：`BigDecimal`
- 每个字段上方写一行中文 Javadoc，取自 DDL 的 COMMENT

### 4.3 Mapper

```java
@Mapper
public interface DevApplicantMapper extends BaseMapper<DevApplicant> {
    // 简单查询用 LambdaQueryWrapper，不写 XML
    // 跨表或需要绕开逻辑删除时才加 @Select / @Delete
}
```

`@MapperScan("com.hparty.**.mapper")` 已在 `MybatisPlusConfig` 配好。

### 4.4 ⚠️ UPDATE 语句的两条禁令（BlockAttack 拦截器）

`MybatisPlusConfig` 注册了 `BlockAttackInnerInterceptor` 防止误写全表更新。
它的判定比名字严格，会对两类**合法**语句抛
`Prohibition of table update operation`：

| 禁令 | 说明 |
|---|---|
| **WHERE 里不要有 `OR`** | 即使是 `AND (a OR b)` 这种带括号的分组也会被拒 |
| **WHERE 里不要有 `<>`（`.ne()`）** | **仅当该表有 `del_flag` 时触发** —— 它的内部判定把 `列 <> ?` 误认为恒真条件，与 MP 自动追加的 `del_flag = ?` 相与后判定为「无有效 WHERE」 |

第二条尤其隐蔽：**同一句写法在没有 `del_flag` 的表上完全正常**，
所以很难从报错联想到原因。

**正确写法**：条件判断放 Java 侧，UPDATE 只用 `IN`：

```java
// ✗ WHERE status <> ? OR ... —— 会被拦
// ✓ 先 SELECT 主键，再 UPDATE ... IN (ids)
List<Long> ids = mapper.selectList(new LambdaQueryWrapper<T>()
        .select(T::getId).ne(T::getStatus, X)).stream().map(T::getId).toList();
if (!ids.isEmpty()) {
    mapper.update(null, new LambdaUpdateWrapper<T>().set(T::getFlag, 0).in(T::getId, ids));
}
```

- **SELECT 不受限制**（拦截器只管 UPDATE/DELETE），查询里 OR 和 `<>` 随便用
- 等价替换也行：`is_overdue <> 1` → `is_overdue = 0`（NOT NULL DEFAULT 0 时）
- **不要摘掉这个拦截器** —— 它能挡住真正的全表更新，在党费、党员数据上误写一次后果严重
- 自定义 `@Update` 注解 SQL 不经过这套判定，是另一条可行的出路

## 五、Controller 约定

```java
@Tag(name = "10-发展党员")                    // 序号 + 模块名，用于接口文档分组
@RestController
@RequestMapping("/develop/applicant")
@RequiredArgsConstructor
public class DevApplicantController {

    private final DevApplicantService applicantService;

    @Operation(summary = "发展党员卡片墙分页")
    @SaCheckPermission("develop:applicant:list")            // 功能权限
    @OperLog(title = "发展党员", businessType = OperLog.BusinessType.INSERT)  // 审计日志
    @PostMapping
    public R<Long> add(@Valid @RequestBody DevApplicantDTO dto) {
        return R.ok("新增成功", applicantService.add(dto));
    }
}
```

- **每个写操作都要有 `@SaCheckPermission`**，权限标识必须已在 `sys_menu` 里种下
- **关键写操作加 `@OperLog`**（用户管理、角色管理、发展党员办理已有；其余模块待补）
- 密码等敏感参数用 `saveRequestData = false` 关掉参数记录
- 方法上写 `@Operation(summary = "...")`，类上写 `@Tag(name = "序号-模块名")`

## 六、前端约定

### 6.1 API 层

一个模块一个文件（`src/api/xxx.ts`），导出类型定义 + 请求函数：

```ts
import { http } from './request';
import type { PageQuery, PageResult } from '@/types/api';

export interface XxxVO { /* ... */ }
export interface XxxQuery extends PageQuery { /* ... */ }

export const pageXxx = (params: XxxQuery) =>
  http.get<PageResult<XxxVO>>('/party/xxx/page', params);
```

`http` 的拦截器**已经解包** `R<T>`，`http.get<T>()` 直接拿到 `T`，不需要再取 `.data`。

### 6.2 页面结构

- 每页 `export default function XxxPage()`，**不要自己包 Layout**
- 两段式：顶部 `Card` 放工具栏（新增/编辑/删除/刷新），下面 `Card` 放表格或内容
- 新增/编辑复用同一个 `Modal` + `Form`，靠 `editing` 状态区分
- 删除走 `modal.confirm`（从 `App.useApp()` 取 `modal` 与 `message`，不要直接 import 静态方法）
- 表格：`rowKey` + `size="middle"` + `pagination={{ pageSize: 10, showSizeChanger: false }}`
- 日期用 `dayjs`，提交时 `.format('YYYY-MM-DD')`

### 6.3 按钮级权限

```tsx
const can = useUserStore((s) => s.can);
{can('develop:applicant:add') && <Button type="primary">新增</Button>}
```

`can()` 对超级管理员无条件放行。

### 6.4 路由：菜单如何映射到页面

后端 `/auth/routers` 下发菜单树，`src/router/AppRoutes.tsx` 用
`import.meta.glob('../pages/**/*.tsx')` 按 `component` 字段匹配页面文件。

**菜单表的 `component` 必须是纯组件路径**（如 `meeting/index`），
带上查询串（`meeting/index?type=X`）就会匹配不到文件、路由不注册、菜单变死链。

**多个菜单共用同一页面时，筛选项从 URL 路径推导**：

```tsx
// src/pages/meeting/index.tsx
const PATH_TO_TYPE: Record<string, string> = {
  'member-assembly': 'MEMBER_ASSEMBLY',
  'branch-committee': 'BRANCH_COMMITTEE',
  // ...
};
const activeType = PATH_TO_TYPE[location.pathname.split('/').pop() ?? ''] ?? '';
```

这样 `/meeting/member-assembly` 与 `/meeting/party-lecture` 复用同一组件但展示不同数据，
且 URL 即状态（可直接分享、刷新不丢）。

## 七、新增一个业务模块的完整步骤

1. **新增 Flyway 迁移**：在 `hparty-admin/src/main/resources/db/migration/` 新建下一个版本的脚本，
   加表、字段、索引及必要的系统数据。不要改已应用的迁移，也不要在共享库手工执行 `ALTER`。
   `sql/01-schema.sql`、`sql/02-init-system.sql` 只是 V1/V2 的参考副本，不参与执行。
2. **同步文档**：更新 `docs/03-数据库设计.md` 与接口清单；若有逻辑删除 + 唯一约束，
   用生成列（见 `docs/03-数据库设计.md` 2.2）。
3. **配置菜单权限**：目录 `M` / 菜单 `C` / 按钮 `F` 写入新的迁移脚本。
   `component` 必须是纯组件路径，按钮 `perms` 要与 Controller 上的
   `@SaCheckPermission` 完全一致。
4. **后端**：`entity` → `mapper` → `service` → `controller`。列表加 `DataScopeHelper.apply`，
   按主键的操作加 `canAccessOrg`。
5. **按需加演示数据到 `sql/03-init-demo.sql`**，仅用于开发环境，不能放真实个人数据。
6. **前端**：`src/api/xxx.ts` → `src/pages/xxx/index.tsx`。文件路径要与菜单的
   `component` 对上。
7. **验证**：在非生产数据库验证迁移，后端运行受影响模块测试，前端运行
   `npm run build`，并实际调接口确认正常及越权场景。提交 PR 前按
   `CONTRIBUTING.md` 同步最新 `origin/dev` 并重新验证。
