## 12. 2026-09-16 PARTY_SECRETARY 权限种子漂移修复记录

## 13. 2026-09-17 文件预览匿名访问 P0 修复记录

### 根因

`/file/preview/**` 原本位于 `SaTokenConfig.WHITE_LIST`，`FileController` 仅做软登录检查，`SysFileService.preview()` 即使查不到 `sys_file` 元数据也会直接按路径读取磁盘文件。安全边界实际依赖“UUID 文件名难猜 + 路径规范化”，一旦 URL 泄露即可匿名读取文件，也无法按文件所属组织执行数据权限。

### 修复实现

- 从 `SaTokenConfig.WHITE_LIST` 移除 `/file/preview/**`；
- `FileController.preview()` 显式增加 `@SaCheckLogin`；

## 16. 待修缺陷：权限等级与实际可做操作不符（2026-09-25 记录，未修复）

### 16.1 现象

用户报告：普通成员账号可以执行超出其权限等级的写操作，例如发展党员流程中「同意申请」一类的办理动作（越级办理）。

**本节以下内容全部是静态核实**（阅读 Java 源码与 Flyway 迁移脚本），**没有在运行态复现**。核实结论与用户报告不完全吻合，差异见 16.4。

### 16.2 已核实：权限链路本身是逐项授予、无传导的

- 登录时由 `AuthService` 组装 `LoginUser`，权限来自 `AuthMapper.selectPerms`；该 SQL 直接
  `sys_menu JOIN sys_role_menu JOIN sys_user_role`，**不存在父菜单向子菜单的权限传导**，
  `perms` 为空或菜单停用都不计入；
- 发起校验的是 `StpInterfaceImpl`，取会话里的 `LoginUser.getPerms()`；超管返回 `*` 通配；
- 因此 `sys_menu` 里父子关系的**唯一作用**是界面展示，不产生授权。授予菜单 `301`
  （`develop:applicant:list`）不会带出它的子项 `3014`（`develop:applicant:handle`）。

### 16.3 已核实：两处结构性风险点

**风险点 1 —— fail-open：`handle_roles` 为空即放行。** `DevFlowService.checkHandlePermission`
（`hparty-develop/.../DevFlowService.java` 第 781-784 行）：

```java
String roles = step.getHandleRoles();
if (roles == null || roles.isBlank()) {
    return;   // 只要求功能权限 + 数据范围，不再校验「该不该你办」
}
```

当前种子里 25 个步骤都配了 `handle_roles`，所以暂不触发。但任何人只要通过菜单/数据维护改动
`dev_step`，或将来新增步骤时漏配，这一步就立刻对**所有**持有 `develop:applicant:handle` 的账号开放，
且没有任何提示 —— 权限边界默认敞开而非默认关闭。

**风险点 2 —— 组织类标记只判「级别」，不判「对应关系」。** `matchesToken`
（同文件第 798-813 行）把 `PARENT_ORG` / `GRANDPARENT_ORG` / `COUNTY_ORG` 一律交给
`LoginUser.isCommitteeLevel()`，而它的实现是 `orgType != null && orgType == 1`
（`hparty-framework/.../LoginUser.java` 第 65-67 行）—— **只判断用户所属组织是不是党委级，
不判断它是不是该申请人的对应上级党委**。STEP_04 / STEP_08 / STEP_11 这类「上级党委备案/审批」
步骤的身份校验，实际是靠 `checkOrgAccess` 里的 `data_scope` 兜住的。种子数据里恰好看不出问题
（`PARTY_SECRETARY` 的 data_scope=3「本级及以下」，语义与「自己的下辖」重合），
但这是**巧合而非校验**：数据范围一旦放宽（例如自定义范围、或将来多角色取最宽），
党委级账号就能办理不属于自己的下级申请。

### 16.4 未核实：静态复核没有复现出报告中的路径

按种子数据与源码逐条推演，普通党员**不应该**能办理任何步骤：

- `sys_role_menu` 只给 `PARTY_MEMBER`（role_id=9）授予了 menu `301`，其 `perms` 是
  `develop:applicant:list`；`develop:applicant:handle`（menu 3014）**没有授予**；
- role_id=9 的 `data_scope=4`（仅本人），`checkOrgAccess` 会挡掉他人的申请；
- `DevFlowController` 的两个写接口（`/handle`、`/preview`）都带
  `@SaCheckPermission("develop:applicant:handle")`；
- 全模块扫描了一遍 Controller 的写接口与权限注解配比，缺注解的只有：`AuthController`
  （登录/登出/改密，本就不该要权限）、`FileController`（类注释说明文件是共用基础设施，
  改由 `SysFileAccessPolicy` 做资源级授权，见 15.4）、`DevMaterialController`
  （类注释说明刻意不用单一权限注解，改由服务端能力判定，见 15.3）—— 后两者是既有设计，非缺陷。

所以「普通成员可越级」若要成立，最可能是下列之一，**需要在运行库上验证后才能定位**：

1. **运行库授权已偏离种子数据** —— `sys_role_menu` / `sys_role.data_scope` 被手工或脚本改动过
   （本次本地 MySQL 凭据不可用，未能查证）；
2. 现象来自**另一个入口**，并非 `POST /develop/flow/handle`（例如组织关系转接、入党申请接收等同名动作用词）；
3. 前端按钮的**显示**问题（权限断链，第 5 节修过一次），实际点击并未成功。

**修复前需要补充的信息**：具体账号、页面、操作步骤，以及该次操作在 `sys_oper_log` 中的记录
（`handle` 已带 `@OperLog`，`business_type` 为 APPROVE，成功与失败都会留痕），
可用于区分「接口放行」与「前端误显示」。

### 16.5 建议修复方向

1. `checkHandlePermission` 改为 fail-closed：`handle_roles` 为空时**拒绝**并记配置错误日志，
   而不是放行；
2. 组织类标记从「级别判定」收紧到「对应关系判定」——校验该用户所属组织是否为该申请人的
   直接/对应上级，不再依赖 `data_scope` 兜底；
3. 补一组**角色 × 步骤矩阵**的集成回归：正向（该办的能办）+ 反向（不该办的一律 403），
   写法可参照 `DevelopMaterialSubmissionRegressionTest` 与 `AmTaskCrudRegressionTest`。

## 17. 待修缺陷：新增发展对象缺少人员身份校验与跨组织约束（2026-09-25 记录，未修复）

### 17.1 现象

用户报告，在「新增发展对象」时同时存在三个问题：

1. 选人列表**只显示姓名与所属支部**，看不出该人是否已经是党员；
2. 可以**越级添加**发展对象；
3. **已经是党员的人也能被加进发展对象**。

以下为**静态核实**（阅读前后端源码），未做运行态复现。三条的性质并不相同：
第 1 条纯前端即可解决，第 2、3 条必须加后端校验 —— 仅改前端等于没修。

### 17.2 已核实：党员身份是在前端被丢弃的（第 1 条）

数据源本身带着党员状态，是前端映射时丢掉的：

- 后端 `PartyPerson` 有 `memberStatus`（第 72 行）与 `isMember`（第 78 行）两个字段；
- 前端 `PartyPerson` 类型也已经有 `memberStatus` / `memberStatusLabel` / `isMember`
  （`hparty-web/src/api/system.ts` 第 27、28、30 行）；
- 但选人列表用的 `listPersonOptions()`（`hparty-web/src/api/system.ts` 第 91-98 行）
  **只映射了 `personId` / `name` / `orgName` 三个字段**，`PersonOption` 接口也就只有这三项；
- 于是下拉项的文案是 `姓名（支部名）`（`hparty-web/src/pages/develop/applicant.tsx` 第 268-272 行），
  党员身份无处可显。

**结论：第 1 条改前端即可，后端不用动。** 扩 `PersonOption` + 在 label 上带出党员状态，
并让已经是党员的选项**置灰**（与「本人，不可选」同样的处理方式，该处已有先例）。

### 17.3 已核实：后端不校验「是否已是党员」（第 3 条）

`DevApplicantService.add`（`hparty-develop/.../DevApplicantService.java` 第 618-674 行）
目前只校验四件事：

1. 不能把本人添加为发展对象（第 624-627 行，前端置灰 + 后端兜底）；
2. 同一 person 只能有一条发展记录，含逻辑删除残留的物理清理（第 639-651 行）；
3. 目标组织在当前账号数据范围内（第 662 行）；
4. `orgId` 不能为空（第 658-661 行）。

**没有任何一处读取 `party_person.is_member` / `member_status`。** 已经在册的正式党员、
预备党员都可以被创建成发展对象，这在业务上是硬错误 —— 发展党员流程的对象前提就是「尚未入党」。

**口径提醒**：校验不能写成「`is_member` 非 1 才放行」这种半吊子。**预备党员也是党员**
（预备期只是党龄起算不同），以及保留党籍、停止党籍等状态同样不应进入发展流程；
具体哪些 `member_status` 取值算「已是党员」需要业务确认后写成显式白名单，
不要用「非空即拒绝」之类想当然的写法。

### 17.4 已核实：跨组织添加只校验目标组织，不校验被添加人（第 2 条）

第 662 行传的是目标组织：

```java
if (!DataScopeHelper.canAccessData(orgId, dto.getPersonId())) {
    throw BizException.forbidden("无权在指定党组织下创建发展对象");
}
```

而 `DataScopeHelper.canAccessData`（`hparty-framework/.../DataScopeHelper.java` 第 142-152 行）
对非 SELF 范围**退化成 `canAccessOrg(targetOrgId)`**，`personId` 参数实际不参与判定。
于是留下两个口子：

1. **不校验被添加人自己的 `org_id` 与目标组织是否一致** —— 可以把 A 支部的人挂到 B 支部去发展。
   前端选人列表走 `/system/person/page`（受数据范围过滤），低权限账号通常看不到外支部的人，
   但**接口层没有这个保证**，直接构造请求即可绕开；
2. `data_scope=3`（本级及以下）的党委书记可以往**任意下辖支部**塞人。
   这算不算「越级」取决于业务约定 —— 发展对象应由其所在支部发起还是上级可代办，
   需要业务先明确，再决定是收窄到「目标组织 = 被添加人所在组织」还是保留上级代办能力。

前端第 268-272 行的「本人，不可选」置灰只覆盖了本人这一种情况，
跨组织人员**没有任何置灰或提示**。

### 17.5 修复方向

1. **前端**：`PersonOption` 增加党员状态字段并在选项上显示；已是党员的置灰不可选
   （复用「本人，不可选」的既有写法）；
2. **后端加身份校验**：`add` 里读取 `party_person`，命中「已是党员」的状态即拒绝，
   错误信息说清原因（例如「张三已是正式党员，不能重复纳入发展流程」）；
3. **后端加组织一致性校验**：明确业务口径后，校验被添加人所属组织与目标组织的关系，
   并把 `canAccessData` 退化为 `canAccessOrg` 这件事显式化 —— 该处需要 personId 参与判定时，
   不要依赖这个会退化的方法；
4. **补回归**：新增用例覆盖「已是党员被拒」「跨组织被拒」「预备党员被拒」，
   写法可参照 `AmTaskCrudRegressionTest`。
