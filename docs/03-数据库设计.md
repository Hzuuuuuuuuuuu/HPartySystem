# 数据库设计

> **结构与数据的分工**：数据库由 **Flyway** 管理，迁移脚本在
> `hparty-server/hparty-admin/src/main/resources/db/migration/`
> （`V1__init_schema.sql` 建表 49 张、`V2__init_system_data.sql` 系统数据）。
> **加表/加列请按现有最大版本号新增下一版迁移，不要改已应用的迁移，也不要手工 ALTER。**
>
> `sql/01-schema.sql` 与 `sql/02-init-system.sql` 是可读的参考副本，不参与执行；
> `sql/03-init-demo.sql`（演示数据）不是迁移，需手工执行。

## 一、总览

- 数据库 **MySQL 8.0**，字符集 `utf8mb4` / 排序规则 `utf8mb4_general_ci`，引擎 `InnoDB`，库名 `hparty`。
- 共 **49 张表**，按业务域分为 12 组。
- 命名前缀即域标识：`sys_` 系统、`party_` 人员/党费、`dev_` 发展党员、`am_` 三会一课、`org_` 换届、`edu_` 教育、`discipline_` 党纪、`member_` 服务、`excellent_` 评选。
- **不用外键**（`SET FOREIGN_KEY_CHECKS = 0` 建表），关联靠 `xxx_id` 逻辑引用 + 索引；级联删除/一致性由 Service 层保证。

| 域 | 表数 | 表名 | 用途 |
|---|---|---|---|
| **系统域** | 12 | `sys_dept` `sys_user` `sys_role` `sys_user_role` `sys_role_dept` `sys_menu` `sys_role_menu` `sys_dict_type` `sys_dict_data` `sys_login_log` `sys_oper_log` `sys_file` | 组织树、RBAC 鉴权、字典、日志、文件 |
| **人员域** | 4 | `party_person` `party_member_profile` `party_position` `party_group` | 人员统一档案 + 党员扩展信息 + 任职记录 + 党小组 |
| **发展党员域** | 14 | `dev_stage` `dev_step` `dev_applicant` `dev_step_record` `dev_material` `dev_talk` `dev_vote` `dev_political_review` `dev_training` `dev_approval` `dev_archive` `dev_plan` `dev_plan_quota` `dev_material_template` | 5 阶段 25 步流程引擎（配置 2 张 + 实例 1 张 + 流水 1 张 + 佐证 7 张）+ 年度计划与指标分解 2 张 + 材料模板 1 张 |
| **会议域** | 5 | `am_meeting` `am_attendee` `am_material` `am_task` `am_task_submit` | 三会一课 / 主题党日 / 组织生活会 + 活动任务通知 |
| **换届域** | 2 | `org_election` `org_election_candidate` | 换届选举记录 + 候选人/当选情况 |
| **教育域** | 2 | `edu_activity` `edu_participant` | 党员教育活动 + 参与记录 |
| **党纪域** | 2 | `discipline_study` `discipline_participant` | 党纪学习教育 + 参与记录 |
| **党费域** | 2 | `party_dues_record` `party_dues_use` | 党费缴纳（一人一月一条）+ 党费使用 |
| **服务域** | 1 | `member_service` | 党员服务/帮扶记录 |
| **评选域** | 2 | `excellent_selection` `excellent_candidate` | 先优评选活动 + 候选人 |
| **评议域** | 2 | `party_review` `party_review_detail` | 民主评议党员批次 + 一人一条的评议明细 |
| **转接域** | 1 | `party_transfer` | 组织关系转接单（转出/转入/内部调整），含介绍信号与有效期 |

**若干「一对多」的固定套路**：`主表(org_id + 业务字段 + 统计列)` → `子表(主表id + person_id + 参与/结果列)`。
`am_attendee` / `edu_participant` / `discipline_participant`（参与类，带 `attend_status` / `score` / `is_passed`）与 `org_election_candidate` / `excellent_candidate`（结果类，带 `votes` / `rank_no` / `result`）都遵循这个形状，新增同类模块时照此办理即可。
注意「参与类」子表的保存一律是**全量替换**（先删旧名单再插新名单），并**回写主表的 `actual_attend`**（见 §5.1）。

## 二、贯穿全局的设计约定

> 这一节是接手时最该先读的部分。违反了这些约定，代码能跑但会留下难查的坑。

### 2.1 审计字段与 BaseEntity

`com.hparty.common.core.BaseEntity` 定义 5 个字段：

| 字段 | 填充方式 |
|---|---|
| `create_by` | `FieldFill.INSERT`，由 `MetaObjectHandler` 自动填当前登录人 |
| `create_time` | `FieldFill.INSERT` |
| `update_by` | `FieldFill.INSERT_UPDATE` |
| `update_time` | `FieldFill.INSERT_UPDATE` |
| `del_flag` | `@TableLogic`，逻辑删除标志（0=存在 1=删除），且 `select = false`（不查出到实体里） |

**只有 DDL 里同时具备这 5 列的 13 张表才继承 `BaseEntity`**（列不齐就继承会导致 MyBatis-Plus 生成引用不存在列的 SQL）：

```
sys_dept          sys_user           sys_role           party_person
dev_applicant     am_meeting         org_election       edu_activity
discipline_study  party_dues_record  party_dues_use     member_service
excellent_selection
```

**其余表的处理方式**（三类），新增表时**必须逐列对照 `01-schema.sql` 再决定走哪条路，不要照抄别的实体**：

1. **有四列审计字段但没有 `del_flag`** —— `sys_menu`、`sys_dict_type`、`sys_dict_data`。这三张表在实体里**自行声明** 4 个审计字段（不继承 `BaseEntity`），因为不需要逻辑删除。
2. **有 `del_flag` 但审计列不齐** —— `sys_file`（只有 `create_time`）、`party_group`（`create_time`+`update_time`）、`am_material`（`create_time`）、`am_task`（`create_time`+`update_time`）、`dev_material`（`create_by`+`create_time`）。这些实体自行声明字段，并在 `delFlag` 上单独打 `@TableLogic`。
3. **完全没有审计列** —— 纯关联表 `sys_user_role` / `sys_role_dept` / `sys_role_menu`（只有两列联合主键，无实体类，直接用 Mapper 操作）；流水表 `dev_step_record`、`dev_talk`、`dev_vote`、`dev_political_review`、`dev_training`、`dev_approval`、`dev_archive`、`am_attendee`、`am_task_submit`、`org_election_candidate`、`edu_participant`、`discipline_participant`、`excellent_candidate`（只留 `create_time`，业务上一经写入不再修改，**不需要 `update_by`/`update_time`**）；日志表 `sys_login_log` / `sys_oper_log`（用语义化的 `login_time` / `oper_time` 代替 `create_time`）；模板表 `dev_stage` / `dev_step`（静态配置，由 `02-init-system.sql` 重建，不需要审计）。

> **注意**：49 张表中有 46 张有对应实体类（`domain/entity/`），3 张纯关联表没有。
> 其中 `party_review` / `party_review_detail`（`hparty-party`）、`dev_plan` / `dev_plan_quota`（`hparty-develop`）
> 在 2026-09 新增，`hparty-system` 的统计报表导出另建了 4 个**只读最小投影**实体映射到
> `party_dues_record` / `dev_applicant` / `am_meeting` / `party_review_detail`（见 §2.1 的 `PartyFile` 思路）。
> 另外 `hparty-party` 模块为了不反向依赖 `hparty-system`，写了一个 `PartyFile` 实体**也映射到 `sys_file`**（最小字段集投影，配合注解 SQL 写入）。改 `sys_file` 表结构时**两个实体都要同步**。

### 2.2 逻辑删除与唯一约束的配合（**重点，最容易踩坑**）

系统里多张表既是逻辑删除（`del_flag`），业务上又需要唯一约束（账号不能重名、一人只能有一条发展流程…）。

**若唯一索引直接建在业务列上，被逻辑删除的墓碑行会一直占用索引**，导致"删掉之后再也建不出同名记录"，而且报的是无信息量的 500。

**方案 A（推荐，已应用于 4 张表）：生成列 + 唯一索引**

```sql
`username_alive` VARCHAR(64) GENERATED ALWAYS AS (IF(`del_flag` = 0, `username`, NULL)) VIRTUAL,
UNIQUE KEY `uk_user_username_alive` (`username_alive`)
```

**原理**：逻辑删除后生成列变成 `NULL`；MySQL 的唯一索引**对多个 NULL 放行**，所以墓碑行可以无限多、互不冲突，而存活行之间仍然唯一。

已应用的表：

| 表 | 生成列 | 唯一索引 |
|---|---|---|
| `sys_user` | `username_alive` | `uk_user_username_alive` |
| `sys_role` | `role_key_alive` | `uk_role_key_alive` |
| `party_person` | `id_card_alive` | `uk_person_id_card_alive` |
| `party_dues_record` | `dues_key_alive` = `CONCAT(person_id,'-',dues_year,'-',dues_month)` | `uk_dues_person_month_alive` |

> `party_person.id_card_alive` 这一列对多个 NULL 放行，因此**"不填身份证"的人员录入不受影响**——这正是选生成列而不是"把 id_card 改成 NOT NULL"的原因。

**方案 B（特例，仅 `dev_applicant`）**：`uk_applicant_person(person_id)` 仍直接建在业务列上，靠代码在 `DevApplicantService.add()` 里**物理清理墓碑行**：

- `DevApplicantMapper.selectAllByPersonId()` 用注解 SQL **绕过 `@TableLogic`**，把含 `del_flag=1` 的行也查出来；
- 有存活行 → 抛明确业务异常；只剩墓碑 → `hardDeleteById()` + `hardDeleteRecords()` 物理删除后重建。

**新增带「逻辑删除 + 唯一约束」的表时，优先用方案 A**；只有当唯一键涉及多列拼接、或清理墓碑时必须连带清理子表数据时，才考虑方案 B，并**务必照抄上面的"先查含删除行再决定"逻辑**（普通 `selectCount` 会自动追加 `del_flag = 0`，看不出墓碑）。

### 2.3 组织树与物化路径

`sys_dept` 是一棵树（党委 → 党总支 → 党支部 → 党小组），用**物化路径**而非递归查询来支撑数据权限：

| 列 | 形态 | 说明 |
|---|---|---|
| `parent_id` | `0` = 根 | 邻接表，用于建树/选父节点 |
| `ancestors` | `0,1,3` | 祖级列表，前端展示面包屑用 |
| `org_path` | `/1/3/7/` | **物化路径，数据权限的核心** |

- **前缀匹配即可拿到整棵子树**，无需 `WITH RECURSIVE`：
  `DataScopeHelper` 在 `data_scope=3`（本级及以下）时追加 `org_id IN (SELECT org_id FROM sys_dept WHERE del_flag=0 AND org_path LIKE #{我的路径} || '%')`。
- **结尾斜杠是关键**：`/1/2/` 不会误配 `/1/23/`。少写这个斜杠就会把兄弟节点串进来。
- 索引 `idx_dept_path (org_path(191))` 是**前缀索引**，只取前 191 字符，够用且省空间。
- `DataScopeHelper.canAccessOrg()` 做详情/改/删的越权校验时，用 `OrgPathResolver.orgPathOf(targetOrgId)` 取目标路径，判断"目标路径以我的路径为前缀"——**不能只判断自己的 orgPath 非空就放行**（早期版本这里是越权漏洞，兄弟支部也能按 ID 访问）。

**维护责任在 `SysDeptService`**：新增组织落库后回填 `orgPath`/`ancestors`（先给占位 `/`，拿到自增主键后才能算出真实路径）；**修改父节点时调用 `cascadeUpdateChildren()` 级联重写整棵子树的 `orgPath` 与 `ancestors`**——改父不改子会让数据权限漏掉整棵子树。另外还会校验"不能把父节点挂到自己的子孙下"（防成环）。

### 2.4 人员用一张表打通全生命周期

`party_person.member_status` 是**贯穿全系统的核心状态**：

```
0=群众 → 1=入党申请人 → 2=入党积极分子 → 3=发展对象 → 4=预备党员 → 5=正式党员
                                                              ↘ 6=流动党员
```

**为什么不做成"申请人表 + 党员表"两套**：同一个人在不同阶段会被不同模块引用（发展党员流程、党费、会议签到、评选），两套表意味着要么数据打架、要么到处做 `UNION`。一张表 + 一个状态列，所有下游模块只需要认 `person_id`。

- `is_member`（是否党员）是 `member_status` 的派生量，由 `PartyPersonService.normalize()` 在保存时根据 `MemberStatus.isPartyMember()` 自动同步，**不要手工设**。
- 各阶段的时间点单独成列：`apply_date` / `activist_date` / `candidate_date` / `probationary_date` / `full_member_date`——既用于展示，也是 `DEADLINE_RULE`、`INTERVAL_RULE`、`PROBATION_PERIOD_RULE` 的计算依据。**发展党员流程推进时会回写这些列**，它们是"跨模块可读的里程碑"，而不只是流程内部的记录。
- 党员才有的信息（介绍人、培养联系人、党费基数、党内职务、流动去向、档案存放地）拆到 `party_member_profile`，`person_id` 上唯一约束，`member_status >= 4` 时有意义。**这样群众/申请人的档案不会带着一堆永远为空的列**。
- 党小组通过 `party_person.group_id` 关联 `party_group`。

### 2.5 枚举值与字典

**两套机制并存，各司其职**：

| 机制 | 位置 | 用途 |
|---|---|---|
| **Java enum** | `com.hparty.common.enums`、`com.hparty.party.enums` | 后端**流转判断**，`if (status == MemberStatus.MASS.getCode())` |
| **数据字典** | `sys_dict_type` / `sys_dict_data` | 前端**下拉选项与表格回显**，可在后台增删改 |

**`com.hparty.common.enums`（6 个，跨域通用）**：`DataScope`（数据范围）、`OrgType`（组织类型）、`MemberStatus`（人员状态）、`MeetingType`（会议类型）、`HandleResult`（办理结论）、`MaterialCategory`（组织生活会材料分类）。

**`com.hparty.party.enums`（15 个，党务域专用）**：`AttendStatusEnum`、`ElectionTypeEnum`、`ElectionStatusEnum`、`EduActivityTypeEnum`、`EduActivityStatusEnum`、`DisciplineStudyTypeEnum`、`DisciplineStatusEnum`、`DuesStatusEnum`、`DuesPayTypeEnum`、`DuesUseCategoryEnum`、`ServiceTypeEnum`、`ServiceStatusEnum`、`ExcellentTypeEnum`、`ExcellentStatusEnum`、`ExcellentResultEnum`。

**`com.hparty.develop` 没有 enums 包**：发展域的状态常量直接写成 `DevFlowService` 里的 `public static final int`（`STATUS_RUNNING=1` / `STATUS_FINISHED=2` / `STATUS_TERMINATED=3`，记录状态 `RECORD_DONE=1` / `RECORD_TODO=2` / `RECORD_CANCELLED=3`），因为这套状态只在本模块内使用、不对外暴露给前端做下拉。

**有 12 类字典**（见 §4），其中 `party_member_status`、`am_meeting_type`、`dev_step_result`、`am_material_category` 等**同时存在对应的 Java enum**——这不是重复：后端用 enum 做判断，前端用字典渲染。字典的 `dict_value` 与 enum 的 `code` 必须保持一致。

> **给新模块加枚举的办理方式**：需要前端下拉/回显 → 往 `sys_dict_type` + `sys_dict_data` 各加一条；需要后端做逻辑分支 → 在对应域的 `enums` 包加一个 enum（带 `code` + `label` + `labelOf()` 静态方法，照抄 `MemberStatus`）。两者都要时**两处都加，且 code 对齐**。

## 三、各域表结构说明

### 3.1 系统域（12 张）

**`sys_dept`** — 党组织树。核心是 `parent_id` + `ancestors` + `org_path` 三件套（见 §2.3）。
班子信息直接冗余在主表上：`secretary_id` / `deputy_id` / `org_committee_id` / `prop_committee_id` / `disc_committee_id`（都指向 `party_person.person_id`），另配 `leader`（负责人姓名快照）。
任职的历史轨迹不放这里，在 `party_position`。
索引：`parent_id`（建树）、`org_path(191)`（数据权限前缀匹配）、`org_type`（按类型统计）。

> **`org_type` 取值**：`1=党委 2=党总支 3=党支部 4=党小组`，另有 **`9=管理节点`**
> （`OrgType.ADMIN_NODE`）。9 **不是党组织**，而是超管的归属组织 —— `sys_user.org_id`
> 会被写进各类业务表的 `NOT NULL` 组织列，超管若没有归属组织就会直接撞数据库约束、
> 报出无信息量的 500。它是 `parent_id = 0` 的独立根，因此真实党组织仍是单棵树
> （`DevPlanMapper#selectRootOrgId` 等「根组织只有一个」的假设不受影响）。
> 该类型**只能由 Flyway `V6__create_admin_org.sql` 创建**：`SysDeptService.validate()`
> 仍只放行 1–4，界面造不出来。所有对外展示处一律按 `org_type = 9` 排除 ——
> 组织分页列表、组织树（含「上级组织」下拉）、党组织总数统计、取根组织；
> 按 ID 的详情/改/删也直接拒绝（`SysDeptService#requireDept`），
> 否则删掉它会带走超管的归属组织。

**`sys_user`** — 登录账号。`person_id` 关联人员档案（**可以为 NULL**：纯管理账号、超管没有人员档案），`org_id` 是数据权限的锚点。
`username_alive` 生成列实现"删除后可重建同名账号"（见 §2.2）。
`password` 存 BCrypt 摘要；`login_ip` / `login_date` / `pwd_update_date` 记录安全审计所需信息。

**`sys_role`** — 角色。`data_scope` 决定数据可见范围（1=全部 2=本级 3=本级及以下 4=仅本人 5=自定义），`DataScopeHelper` 据此翻译成 SQL。
`is_builtin=1` 的角色（10 个预置角色）**不允许删除**。`role_key_alive` 生成列保证删除后可重建同名角色。

**`sys_user_role`** — 用户-角色关联，联合主键 `(user_id, role_id)`，无实体类。
**`sys_role_dept`** — 角色-组织关联，**只在 `data_scope=5`（自定义）时被读取**：`DataScopeHelper` 在 CUSTOM 分支里 `org_id IN (SELECT org_id FROM sys_role_dept WHERE role_id IN (SELECT role_id FROM sys_user_role WHERE user_id = ?))`。

**`sys_menu`** — 菜单 + 按钮权限合一。`menu_type` 区分 M=目录 / C=菜单 / F=按钮，`perms` 是权限标识（如 `develop:applicant:list`），后端靠 `@SaCheckPermission` 校验。
**没有 `del_flag`**（菜单由 `02-init-system.sql` 全量重建）。
**`sys_role_menu`** — 角色-菜单关联，联合主键，无实体类。

**`sys_dict_type` / `sys_dict_data`** — 数据字典。两张表都**没有 `del_flag`**。
`sys_dict_data` 上有 `uk_dict_type_value(dict_type, dict_value)` 唯一索引——Service 层的"先查后插"校验在并发下会漏，缺了索引会出现同键重复行，前端下拉框出现重复项。

**`sys_login_log`** — 登录日志（成功/失败、IP、浏览器、OS）。**只写不改**，用 `login_time` 而非 `create_time`。
**`sys_oper_log`** — 操作日志（由切面写入，含请求参数/返回体/耗时/异常）。同样是 `oper_time`。日志表**不参与数据权限过滤**，仅超管可见（见 `02-init-system.sql` 的菜单备注）。

**`sys_file`** — 文件元数据。**本地磁盘存储，库里只存相对路径**（`file_path`），`storage_type` 预留 `local`/`minio`/`oss` 三种实现。
`biz_type` + `biz_id` 是**通用挂载点**（如 `dev_material`/`meeting`/`avatar`），索引 `idx_file_biz` 支持"查某业务对象的全部附件"。
只有 `create_time` + `del_flag`，没有 `update_*`（文件一经上传不再修改）。
`hparty-party` 模块通过 `PartyFile` 实体（同一张表的最小投影）写入，避免模块间循环依赖。

### 3.2 人员域（4 张）

**`party_person`** — 人员统一档案，全系统的"人"主表（见 §2.4）。
关键列：`member_status`（0-6 生命周期状态）、`is_member`（派生量，保存时自动同步）、五个里程碑日期列、`org_id`（数据权限锚点）、`group_id`（党小组）。
`id_card_alive` 生成列 + `uk_person_id_card_alive` 保证存活行身份证唯一、且允许不填。
索引：`org_id`、`member_status`、`name`。

**`party_member_profile`** — 党员扩展信息，`uk_profile_person(person_id)` 一人一条，`member_status >= 4` 时有效。
存 `introducer1_id` / `introducer2_id`（入党介绍人）、`trainer1_id` / `trainer2_id`（培养联系人）、`volunteer_book_no`（志愿书编号）、`dues_base` / `dues_standard`（党费基数与应缴额）、`party_position`（党内职务）、`is_flow` / `flow_location`（流动党员）、`archive_location`（档案存放地）。
`branch_secretary` 是支部书记**姓名快照**（冗余，见 §5）。

**`party_position`** — 党内职务任职记录，`person_id` + `org_id` + `position_code`。
这是**历史流水表**：`start_date` / `end_date` / `is_current`（`end_date IS NULL` 表示在任），一个人可以有历届多条任职记录。
与 `sys_dept` 上的 `secretary_id` 等字段的关系：`sys_dept` 存"当前是谁"（快照，方便列表展示），`party_position` 存"历任是谁"（完整轨迹）。**换届选举产生新班子时两边都要写**。

**`party_group`** — 党小组，挂在党支部下（`org_id` 指向支部）。`leader_id` 指向党小组长。
`member_count` 是冗余列且**完全不维护**（见 §5）。

### 3.3 发展党员域（12 张）

> 不含年度计划的 2 张（见 §3.12），含材料模板 1 张。

> 这是全系统最复杂的域。流程规则原文见 [02-入党流程25步定义.md](./02-入党流程25步定义.md)，引擎设计动机见 [01-系统设计.md](./01-系统设计.md) §5。

#### 状态机由四张表构成

```
dev_stage   （5 条，静态配置）  阶段模板
   └ dev_step    （25 条，静态配置）  步骤模板：所属阶段 / 办理角色 / 期限 / 规则 key
        ↓ 实例化
dev_applicant    （一人一条）    申请人实例：当前走到哪一步
        ↓ 每次办理产生
dev_step_record  （动态流水）    步骤办理记录：谁、何时、什么结论、下一步去哪
```

- **`dev_stage`** — 5 个阶段的模板（`STAGE_1`..`STAGE_5`），由 `02-init-system.sql` 建立，`uk_stage_code` 唯一。纯配置表。
- **`dev_step`** — 25 个步骤的模板（`STEP_01`..`STEP_25`），是**流程引擎的核心配置**。字段分四类：
  - *定位*：`stage_code`（所属阶段）、`step_order`（1..25 全流程顺序）
  - *办理约束*：`handle_roles`（谁可办，逗号分隔）、`handle_org_type`（哪级组织办：1=党委 2=党总支 3=党支部 4=党小组）、`need_vote`（是否需表决）
  - *时限与周期*：`deadline_days`（办结期限）、`interval_days` + `interval_base_step`（距某步骤须满 N 天）、`periodic_days`（周期性考察间隔）、`min_training_days` / `min_training_hours`
  - **`rule_key`（最关键的列）**：逗号分隔的规则策略 key，绑定到 `DevStepRule` 实现类
  - `step_type`：1=单次办理型 / 2=周期性考察型（只有 `STEP_06`、`STEP_21` 是 2）
  - `is_branch`：分支节点标记，**只有 `STEP_23` 为 1**（转正/延长/取消三出口）
- **`dev_applicant`** — 申请人实例，`uk_applicant_person(person_id)` 保证一人只有一条。`current_stage` + `current_step` 指向当前停留位置，`status`（1=进行中 2=已完成 3=已终止 4=已中止），`progress`（按 `step_order` 折算的百分比）。
  里程碑日期（`apply_date` 等五个）与 `party_person` 上同名列**保持一致**——流程推进时同步回写。
  预备期相关：`probation_end_date`（= 预备党员日期 + 1 年，延长后顺延）、`probation_extend_count`（最多 1 次）、`probation_extend_months`（6-12 个月）。
  冗余 `person_id` / `org_id` 之外的 `trainer_ids` / `introducer_ids` 是**逗号分隔的多值列**（1-2 名 / 2 名）。
  唯一约束的处理见 §2.2 方案 B。
- **`dev_step_record`** — 步骤办理流水，**任一时点有且仅有一条"当前待办"**（`status=2`），办结后置 1，作废置 3。
  `seq_no` 区分同一步骤的第几次办理（周期性步骤用）。`result` 是**流转方向的决定者**（1=通过 2=驳回 3=不通过 4=延长 5=取消资格），`next_step_code` 记录实际流转目标。
  `deadline_time` + `is_overdue` 支撑超期预警（`is_overdue` 由 `DevFlowService` 自动计算，见 §5）。
  冗余 `person_id` / `org_id` / `stage_code` / `handle_name`，目的是**让数据权限和列表查询不必回表 join**。

#### 七张佐证表：全部挂在 `applicant_id` 上

这七张表形状一致——`applicant_id`（必填，指向实例）+ `step_code`（哪一步产生的）+ 业务字段，都是"流程产生的证据材料"。**它们不参与流转决策，决策只看 `dev_step_record.result` 与规则引擎**。

| 表 | 对应步骤 | 要点 |
|---|---|---|
| `dev_material` | 全部 | 材料档案（申请书/思想汇报/政审材料/志愿书/转正申请…）。`material_type` 决定归属，`file_id` 指向 `sys_file`，`content` 存文本正文。 |
| `dev_talk` | STEP_02 / STEP_16 | 谈话记录。`talk_type` 区分党组织派人谈话与上级党委派人谈话，含谈话人、地点、内容、结论。 |
| `dev_vote` | STEP_15 / STEP_23 | 支部大会表决。**票数规则双过半**：`quorum_required`（应到半数取整+1）、`pass_required`、`is_quorum_met`、`is_passed` 四个列都由 `DevFlowService` 自动算出（见 §5）。`result_type` + `extend_months` 只在 STEP_23 用（三出口）。 |
| `dev_political_review` | STEP_10 | 政治审查，一人一条。四个 `TEXT` 列对应政审的四项内容（态度/历史/守法/亲属），`review_result` 1=合格 2=不合格。 |
| `dev_training` | STEP_11 | 集中培训，一人可多次。`train_days >= 3`、`train_hours >= 24` 由 `TRAINING_HOUR_RULE` 校验。 |
| `dev_approval` | STEP_04/08/13/17/18/24 | 上级审批备案。`approval_type` 区分 1=备案 2=预审 3=审批，`apply_org_id` / `approve_org_id` 记录申请方与审批方，`is_overdue` 是**死列**（见 §5）。 |
| `dev_archive` | STEP_25 | 材料归档。`archive_type`（1=存入人事档案 2=建立党员档案），`items` 是 JSON 数组形式的归档清单。 |

#### 规则策略的绑定关系（`dev_step.rule_key` → `DevStepRule` 实现）

`DevRuleEngine` 在启动时把所有 `DevStepRule` 实现按 `ruleKey()` 建索引，办理时按 `dev_step.rule_key` 逐个执行。
**改流程规则 ≈ 改 `dev_step` 这张表**——新增/调整步骤只需改数据（必要时加一个策略类），不动主流程代码。

| rule_key | 实现类 | 适用步骤（`02-init-system.sql` 中的实际绑定） |
|---|---|---|
| `MATERIAL_REQUIRED_RULE` | MaterialRequiredRule | 03/04/08/10/12/14/16/18/20/25（必备材料齐全才可提交） |
| `QUALIFICATION_RULE` | QualificationRule | 01/05/09/13（办理人资格） |
| `DEADLINE_RULE` | DeadlineRule | 02（30 天）/ 17（90 天）/ 24（90 天） |
| `INTERVAL_RULE` | IntervalRule | 06（距 STEP_03 满 365 天）、07 |
| `PERIODIC_RULE` | PeriodicRule | 06（每 180 天）、21（每 90 天） |
| `PROBATION_PERIOD_RULE` | ProbationPeriodRule | 21、22（预备期须满 1 年） |
| `TRAINING_HOUR_RULE` | TrainingHourRule | 11（≥3 天或 ≥24 学时） |
| `VOTE_RULE` | VoteRule | 15、23（双过半） |
| `BRANCH_RULE` | BranchRule | 23（三出口分支） |

> `PROBATION_PERIOD_RULE` 在 [01-系统设计.md](./01-系统设计.md) 的规则表里没有列出，但**代码和种子数据里都有**——以本文档和 `02-init-system.sql` 为准。

#### `dev_material_template` —— 材料模板（依据《广西发展党员工作手册》）

**50 条**配置数据，把手册要求的 50 份表格按编号映射到 25 个步骤。

| 字段 | 说明 |
|---|---|
| `template_code` | 模板编号，**与手册附件编号一致**：`1-1`、`1-2-1`、`4-1a`、`5-13` …（`1-x` 属阶段一，依此类推） |
| `step_code` | 挂到哪个步骤；**NULL 表示阶段通用或全程通用**（如 `1-3` 全程纪实表） |
| `is_required` | 是否必备（必备 38 份）。普通党务办理仍保持“缺材料仅提醒、允许后补”的原规则；但申请人专用 `self-submit` 会硬校验当前步骤中 `submit_role=APPLICANT` 的必备个人材料必须齐备后才能推进。 |
| `is_roster` | 是否组织台账/名册（7 份）—— 按组织归档，**不随个人流程流转**，不计入个人齐备度 |
| `submit_role` | 出具方：`APPLICANT` 本人 / `BRANCH` 党支部 / `TRAINER` 培养联系人 / `PARENT_ORG` 上级党委 |
| `blank_file` / `sample_file` | 模板文件名，对应 classpath 下 `material-templates/blank/` 与 `sample/` |
| `fill_note` | 填写说明，取自流程图原文的关键约束 |

**模板文件随 jar 打包**，在 `hparty-admin/src/main/resources/material-templates/`
（`blank/` 50 个空表、`sample/` 14 个填写样例）。**是二进制，不要尝试读写内容。**

> **`dev_material.template_code`（2026-09 新增列）**：用于精确判定「这份材料对应哪份模板」。
> **必须优先于 `material_type` 匹配** —— 50 份模板里 36 份的 `material_type` 都是 `OTHER`，
> 且同一步骤上往往挂着好几份 `OTHER`（STEP_23 有 5 份、STEP_13 有 5 份），
> 只按类型匹配会让上传一份就把同步骤的所有 `OTHER` 都标成"已上传"，
> 「材料齐备度」这个指标就失去意义了。
> 匹配逻辑在 `DevApplicantService.isMaterialUploaded`：先比 `template_code`，
> 未填时退化为 `material_type + step_code`。

**统一材料提交（V5，2026-09-17）**

- Flyway `V5__develop_material_submission_permissions.sql` 新增 `develop:material:submit` 与 `develop:applicant:self-submit` 两个功能权限，不修改 V1-V4。
- `dev_material` 的 `applicant_id/person_id/step_code/material_type/template_code/material_name/file_id/file_url/is_required` 全部由服务端根据 `dev_applicant + dev_material_template` 派生，客户端不得指定归属字段。
- `submit_role=APPLICANT` 只允许申请人本人；`BRANCH` 需要支部办理身份 + `develop:material:submit` + 数据范围；`PARENT_ORG` 需要党委级身份 + 材料管理权限 + 数据范围；`TRAINER` 使用 `dev_applicant.trainer_ids` 的精确人员关系授权。
- `is_roster=1` 的组织台账不允许通过个人材料接口上传；未来步骤禁止提前上传；流程进行中允许按原出具方补录历史步骤材料。
- 单次模板再次上传采用替换语义，仅保留一条有效 `dev_material`；周期性步骤（当前 STEP_06）允许同模板多条材料历史。
- 物理文件先进入 `sys_file`，再写 `dev_material`；后续落库失败时调用文件服务做补偿清理，避免形成业务可见的半成品引用。

### 3.4 会议域（5 张）

**`am_meeting`** — **一张表承载三会一课 + 主题党日 + 组织生活会**，靠 `meeting_type` 区分（`MEMBER_ASSEMBLY` / `BRANCH_COMMITTEE` / `PARTY_GROUP` / `PARTY_LECTURE` / `THEME_PARTY_DAY` / `ORG_LIFE`）。
**为什么不拆表**：这六种会议的结构完全相同（时间地点、主持人、应到/实到、内容、状态），拆成六张表会让统计看板要写六个 `UNION`。
`group_id` 只在党小组会时有值。`status` 是 0=草稿 1=待召开 2=进行中 3=已结束 4=已归档。
`should_attend` / `actual_attend` 是人数冗余列（维护情况见 §5）。`del_flag` 生效。
前端"主题党日"页面复用同一套接口，只固定 `meetingType=THEME_PARTY_DAY`。

**`am_attendee`** — 参会人员与签到。`attend_status`（0=未签到 1=已签到 2=请假 3=缺席），`sign_time`、`leave_reason`。
保存走**全量替换**：`AmMeetingService.saveAttendees()` 先删旧名单再插新名单，同时统计 `attend_status=1` 的人数回写 `am_meeting.actual_attend`。

**`am_material`** — 会议材料。`category` 有 11 类（通知/会前学习/记录/党员剖析材料/党员自评材料/其它内容/问题清单/整改清单/会议记录/民主评议党员/情况报告），对应组织生活会的"九宫格"。
`meeting_id` **可以为 NULL**（组织生活会材料按 `org_id` 归档，不一定挂在某次会议下），所以还有独立的 `org_id` 索引。

**`am_task`** — 活动任务通知（上级向下级发布活动）。`publish_org_id` 发布方，`receive_org_ids` 是**逗号分隔的接收组织 ID**（NULL = 全部下辖），`deadline` 是材料上传截止日期。
**`am_task_submit`** — 支部提交的任务材料，`task_id` + `org_id`。与 `am_task` 是一对多。

### 3.5 换届域（2 张）

**`org_election`** — 换届选举记录。`election_type`（1=换届选举 2=补选 3=委员调整）、`term_no`（届次）、`reason`（届满/缺额）、计划与实际选举日期。
票数相关：`should_attend` / `actual_attend` / `quorum_required` / `is_quorum_met`——**只有前两个是有效数据，后两个从不被计算**（见 §5）。
另有 `approve_org_id` + `approve_date` 记录上级党委批复，`file_id`/`file_url` 存请示/批复文件。

**`org_election_candidate`** — 候选人与当选情况。`position_code` 候选职务（`SECRETARY`/`DEPUTY`/`ORG_COMMITTEE`/`PROP_COMMITTEE`/`DISC_COMMITTEE`），`votes` 得票数，`is_elected` 是否当选，`is_incumbent` 是否现任。
**选举结果要落到 `party_position`（任职记录）与 `sys_dept` 的班子字段上**——这两处不会自动同步。

### 3.6 教育域（2 张）

**`edu_activity`** — 党员教育活动。`activity_type`（1=党课 2=专题培训 3=在线学习 4=实践锻炼 5=集中轮训），含学时、主讲人、地点、`should_attend`/`actual_attend`。
**`edu_participant`** — 参与记录。`attend_status`（同 `am_attendee`）、`study_hours`（实际学时，可能因人而异）、`score` + `is_passed`（考核）。
保存同样是**全量替换 + 回写 `edu_activity.actual_attend`**（见 §5）。

### 3.7 党纪域（2 张）

**`discipline_study`** — 党纪学习教育。`study_type`（1=条例学习 2=警示教育 3=专题党课 4=知识测试 5=案例研讨），统计列 `participant_count` + `pass_count`。
**`discipline_participant`** — 参与记录，`score` + `is_passed`。结构与 `edu_participant` 几乎一致（**没有** `study_hours`、**有** `person_name` 冗余）。

### 3.8 党费域（2 张）

**`party_dues_record`** — 党费缴纳记录，**一人一月一条**，靠生成列 `dues_key_alive = CONCAT(person_id,'-',dues_year,'-',dues_month)` + 唯一索引保证（见 §2.2）。
`dues_base`（月工资收入）→ `dues_standard`（应缴额）由 `PartyDuesCalculator` 按四档费率算出：**3000 以下 0.5%、3000-5000 为 1%、5000-10000 为 1.5%、10000 以上 2%**（分档口径只在这一个类里定义）。
`dues_paid` 实缴、`pay_type` 缴纳方式、`status`（0=未缴 1=已缴 2=免缴 3=补缴）。
`is_overdue` 欠缴标记是**死列**（见 §5）。
索引：`org_id`、`(dues_year, dues_month)`（按月统计）、`status`（催缴）。

**`party_dues_use`** — 党费使用记录。`use_category`（1=党员教育 2=表彰奖励 3=困难帮扶 4=阵地建设 5=订阅报刊 6=其它），`amount` 用 `DECIMAL(12,2)`（比缴纳记录的 `10,2` 宽，因为单笔支出可能较大）。

> 缴纳与使用是两张独立表（金额量级、审批流程、统计口径都不同），**"结余"需要靠查询算，库里不存**。

### 3.9 服务域（1 张）

**`member_service`** — 党员服务/帮扶记录。`service_type`（1=困难帮扶 2=志愿服务 3=走访慰问 4=权益维护 5=就业帮扶 6=其它）。
`person_id` **可以为 NULL**（如面向群体的志愿服务），`amount` 帮扶金额，`handler_id` 经办人，`status`（0=待处理 1=处理中 2=已完成 3=已取消），`result` 办理结果。

### 3.10 评选域（2 张）

**`excellent_selection`** — 先优评选活动。`selection_type`（1=优秀共产党员 2=优秀党务工作者 3=先进基层党组织），`selection_year` 年度，`quota` 表彰名额，`status`（0=草稿 1=推荐中 2=评审中 3=已公示 4=已表彰）。
**`excellent_candidate`** — 候选人。**同时支持个人评选与组织评选**：个人类填 `person_id` + `person_name`，组织类填 `org_id` + `org_name`，两组字段都可为 NULL。
`recommend_org_id` 推荐组织，`deeds` 主要事迹，`votes` + `rank_no` 票数与排名，`result`（0=待评审 1=已推荐 2=已获奖 3=未获奖）。

### 3.11 评议域（2 张，2026-09 新增）

**`party_review`** — 民主评议党员批次。一组织一年度一批（`org_id + review_year` 唯一），
`status`（0=草稿 1=自评中 2=互评中 3=组织评定中 4=已公示 5=已完成），`excellent_quota` 优秀名额。
**`org_id + review_year` 的业务唯一约束建在生成列 `org_year_alive` 上**（§2.2 方案 A）——
批次可逻辑删除，删掉同年批次后必须能重建，墓碑行不能占着唯一键。

**`party_review_detail`** — 一人一条的评议明细。五个分项列 `self_score` / `peer_score` / `mass_score` /
`org_score` / `total_score` 与等次 `grade`（1=优秀 2=合格 3=基本合格 4=不合格）。
**`peer_score` 是增量平均**（`peer_count` 记参与互评人数）—— 表里没有逐条保存「谁给谁打了多少分」的位置，
因此同一名打分人重复提交会被重复计入，这是该表结构的已知取舍。
计分权重与等次阈值集中在 `com.hparty.party.util.ReviewScoreRule`，便于按单位实际调整。

### 3.12 发展党员年度计划（2 张，2026-09 新增）

**`dev_plan`** — 年度计划。`org_id + plan_year` 唯一（同样用生成列 `org_year_alive`），
`plan_count` 计划发展数，`activist_target` 积极分子培养目标数，
`status`（0=草稿 1=已下达 2=执行中 3=已完成），`issue_org_id` 下达组织。
**`dev_plan_quota`** — 指标分解到下级组织，`quota_count` 分配名额。
保存走**全量替换**，并校验「各下级名额之和 ≤ 计划总数」「只能分给本单位的下级组织」。

> **进度口径**：本年度 `dev_applicant` 中 `current_step` 已达到 STEP_07（确定发展对象）及之后的人数 ÷ `plan_count`。
> 「已达到」用 `dev_applicant.current_step` 关联 `dev_step` 比较 `step_order >= 7` 判定（不硬编码步骤编码）；
> 「本年度」取 `candidate_date`（确定为发展对象日期）所在年份，缺失时退回 `apply_date`；
> 统计范围含计划组织的整棵子树，终止（`status=3`）的流程不计入。

### 3.13 转接域（1 张，2026-09 新增）

**`party_transfer`** —— 组织关系转接单。转出 / 转入 / 内部调整共用一张表，用 `transfer_type` 区分。

| 关键字段 | 说明 |
|---|---|
| `transfer_no` | 转接单号，如 `ZZ-2026-0001`。唯一约束用生成列 `transfer_no_alive`（逻辑删除后释放） |
| `from_org_id` / `to_org_id` | 原组织 / 目标组织。**可见性与越权校验要两个方向都放行** —— 否则接收方看不到转给自己的单子 |
| `letter_no` / `letter_date` / `valid_days` / `expire_date` | 介绍信号、开具日期、有效期（默认 90 天）、失效日 |
| `status` | 0=待提交 1=已开具(待接收) 2=已接收 3=已拒绝 4=已超期 5=已撤销 |

**两条业务规则（改动前务必确认）**：

1. **开具介绍信不改组织关系** —— 只生成介绍信号与有效期，
   `party_person.org_id` 要等**接收**时才变更。过早变更会让党员在落地前就"离开"了原组织。
2. **接收时与发展党员流程联动**：若该人有进行中的 `dev_applicant`，**不重置流程**，
   只把 `dev_applicant.org_id` 迁到新组织。这是流程图「工作、学习单位变动，
   培养教育时间可连续计算」的落地 —— 重置会让人从头再来。

超期（`status=1` 且 `expire_date < 今天`）由定时任务置为 4，并计入「口袋党员」清单。

#### `dev_stage` 与 `dev_step` 是**流程引擎的配置数据**，不是普通业务数据

这两张表就是 §3.3 里那台状态机的**程序**：

- 5 个阶段：申请入党 / 入党积极分子的确定和培养教育 / 发展对象的确定和考察 / 预备党员的接收 / 预备党员的教育考察和转正。

- **`rule_key` 字段绑定规则策略类**（`DevRuleEngine` 按 key 找到 `DevStepRule` 实现并执行）。举例：
  - `STEP_07`（确定发展对象）绑 `INTERVAL_RULE`，配 `interval_days=365` + `interval_base_step=STEP_03` → "距确定为积极分子须满 1 年"；
  - `STEP_23`（转正讨论）绑 `VOTE_RULE,BRANCH_RULE` → 双过半表决 + 三出口分支；
  - `STEP_21`（继续教育考察，周期性）绑 `PERIODIC_RULE,PROBATION_PERIOD_RULE` → 每 90 天记一次 + 预备期满 1 年才可推进。

> **改流程规则主要就是在改这张表**。调整某个步骤受哪些规则约束只需改 `rule_key` 数据；新增一种规则校验才需要加一个 `DevStepRule` 实现类。
> `dev_stage` / `dev_step` 的完整规则原文见 [02-入党流程25步定义.md](./02-入党流程25步定义.md)。

## 五、已知的冗余字段

系统里刻意保留了一批冗余列。**新增功能时请按下表判断"这个值该不该自己维护"**——下面区分了「自动维护」「写入时快照」「从不维护」三类，均已逐处读过代码确认。

### 5.1 会自动维护

| 列 | 维护位置 | 说明 |
|---|---|---|
| `party_person.is_member` | `PartyPersonService.normalize()` | 由 `member_status` 派生，保存时自动同步 |
| `party_person.age` | `PartyPersonService.normalize()` | 保存时按 `birth_date` 重算。**只在写入时算**，所以不修改该人员时年龄不会随生日增长（展示层如需精确值应现算） |
| `party_person.party_age` | `PartyPersonService.normalize()` | 按 `full_member_date` 重算。同理，**只在写入时算**；`full_member_date` 为空时不会覆盖原值 |
| `dev_applicant.progress` | `DevApplicantService` / `DevFlowService` | 按当前 `step_order` 折算的百分比 |
| `dev_step_record.is_overdue` | `DevFlowService`（**唯一一处**，在办结落库前） | 用建待办时算好的 `deadline_time` 与办理时刻比较。代码特意注明了**不能把 `deadline_time` 写成办理时刻**，否则真实的超期事实会被抹掉。**注意**：建待办（`createPendingRecord()`）只写 `deadline_time`、不写 `is_overdue`，所以待办行该列恒为 0；列表上展示的"待办是否超期"是**现算的**（`DevApplicantService` 用 `LocalDateTime.now().isAfter(deadlineTime)`），不是读这一列 |
| `dev_vote.quorum_required` / `pass_required` / `is_quorum_met` / `is_passed` | `DevFlowService` 落库前 | 按「应到半数取整+1」与「赞成票 * 2 > 应到」算出，与 `VoteRule` 同一口径 |
| `am_meeting.actual_attend` | `AmMeetingService.saveAttendees()` | 保存签到名单时统计 `attend_status=1` 的人数回写 |
| `edu_activity.actual_attend` | `EduActivityService.saveParticipants()` | 同上，保存参与名单时回写 |
| 各表的姓名/组织名快照 | 写入时由 `PartyLookupMapper`（或 system 域查询）填好 | 见 5.2 |

### 5.2 只在写入时取快照，之后不跟随源表

这些列是**刻意的反范式**，目的是让列表查询和数据权限**不必回表 join**。源数据改名后它们**不会**跟着变：

- `dev_step_record.person_id` / `org_id` / `stage_code` / `handle_name`
- `am_attendee.person_name`、`edu_participant.person_name`、`discipline_participant.person_name`
- `party_dues_record.person_name`、`org_election_candidate.person_name`、`excellent_candidate.person_name` / `org_name`
- `am_task.publish_org_name`、`sys_dept.leader`（负责人姓名）、`party_member_profile.branch_secretary`（支部书记姓名）
- `am_meeting.host_name` / `recorder_name`、`dev_vote.host_name` / `recorder_name` 等会议类姓名字段

> 这是**有意的取舍**：组织/人员改名后历史记录仍显示当时的姓名，对党务档案来说反而更符合"留痕"的要求。若产品要求显示最新姓名，应在展示层用 `person_id` 现查。

### 5.3 **从不维护**的冗余列（已知问题，接手时注意）

| 列 | 现状 | 建议 |
|---|---|---|
| **`sys_dept.member_count`** | **不会随人员增减更新**。`SysDeptService.addDept()` 只在新增时把 null 置 0，此后没有任何代码再写它；前端表单允许手填。**演示数据填的是 33 / 16 / 16，而按 `party_person` 实际统计为 1 / 17 / 15 —— 对不上**，这正说明它是个谁也不会去更新的列。 | 需要准确值时应改用 `COUNT(*)` 实时查询（如 `PartyPersonService` 的统计接口就是现算的，没有读这一列）。若要保留该列，应在人员增删改、组织变更时同步维护，或加定时任务重算。 |
| **`party_group.member_count`** | **完全不维护**。没有任何 Service 写它，只有演示数据的 `INSERT` 里填过一次。 | 同上，或直接废弃该列。 |
| **`org_election.actual_attend`** | **不计算**。是前端表单字段，用户手填；服务层只把 null 补成 0。 | 与 `org_election_candidate` 的投票数据无关联校验。若要做到会会议那样自动统计，需新增参会人子表。 |
| **`org_election.quorum_required` / `is_quorum_met`** | **不计算**。`OrgElectionService` 仅在为空时置 0，从不按应到/实到推导。 | 需要时应比照 `DevFlowService` 对 `dev_vote` 的做法，在保存时算好写入。 |
| **`dev_approval.is_overdue`** | **死列**。全代码库没有任何一处写它，恒为默认值 0。 | 可参照 `dev_step_record.is_overdue` 的算法在审批保存时补上。 |
| **`party_dues_record.is_overdue`** | **死列**。只在生成/更新账单时被显式置 0，**没有任何地方置 1**，因此永远查不出欠缴。 | 欠缴状态目前实际靠 `status=0`（未缴）+ 账期与当前时间比较现算。若保留该列，需要加一个扫描任务按账期回填。 |

> **给后续 AI 编码代理的提醒**：`member_count` / `actual_attend` / `is_overdue` 这几类名字听起来"应该是自动算的"，
> 但在本项目中**大部分不是**。写新代码读取这些列之前，先按本文档确认它的维护方；
> 需要准确值时**优先实时查询**而不是依赖冗余列。
