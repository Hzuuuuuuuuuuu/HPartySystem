> 版本 v1.0 ｜ 编制日期 2026-09-16 ｜ 状态：**已交付，功能完整，待生产化**

## 1. 项目概述

面向基层党组织的党务管理系统，覆盖「三会一课、主题党日、发展党员、组织生活会、党费管理、党组织基本情况、换届选举、党员教育管理、党纪学习教育、党员服务、先优评选」共 11 个业务模块，外加系统管理。

核心难点是 **发展党员全流程**：依据《中国共产党发展党员工作流程图》（中央组织部组织一局编），共 **5 个阶段、25 个步骤**，含强时间约束（1 年培养期、3 个月审批期）、强票数规则（支部大会双过半）、周期性考察（每半年一次）与分支出口（转正 / 延长预备期 / 取消资格）。

**当前规模**：数据库 49 张表，后端 6 个 Maven 模块，前端 34 个页面。

## 4. 权限模型

### 4.1 三级权限

| 类型 | 说明 | 实现 |
|---|---|---|
| **功能权限** | 能访问哪些菜单/按钮 | `sys_menu` 树 + `sys_role_menu`；前端 `v-perm` 指令，后端 `@SaCheckPermission` |
| **数据权限** | 能看哪些范围的数据 | 角色绑定 `data_scope`；`sys_dept` 用 `org_path` 物化路径，拦截器按前缀过滤 |
| **字段权限** | 敏感字段可见性 | 预留（如身份证号、政审材料） |

### 4.2 数据范围（data_scope）

| 值 | 名称 | SQL 过滤条件 |
|---|---|---|
| 1 | 全部数据 | 不追加条件 |
| 2 | 本级数据 | `org_id = #{currentOrgId}` |
| 3 | 本级及以下 | `org_path LIKE CONCAT(#{currentOrgPath}, '%')` |
| 4 | 仅本人数据 | `person_id = #{currentPersonId}` |
| 5 | 自定义 | `org_id IN (SELECT org_id FROM sys_role_dept WHERE role_id = ...)` |

### 4.3 预置角色

| 角色编码 | 角色名称 | 数据范围 | 说明 |
|---|---|---|---|
| `SUPER_ADMIN` | 超级管理员 | 全部 | 组织部/系统管理 |
| `PARTY_SECRETARY` | 党委书记 | 本级及以下 | 下辖全部支部 |
| `BRANCH_SECRETARY` | 支部书记 | 本级 | 本支部全部数据 |
| `BRANCH_DEPUTY` | 支部副书记 | 本级 | |
| `ORG_COMMITTEE` | 组织委员 | 本级 | 发展党员主要办理人 |
| `PROP_COMMITTEE` | 宣传委员 | 本级 | |
| `DISC_COMMITTEE` | 纪检委员 | 本级 | |
| `GROUP_LEADER` | 党小组长 | 本级 | |
| `PARTY_MEMBER` | 普通党员 | 仅本人 | |
| `APPLICANT` | 入党申请人/积极分子/发展对象/预备党员 | 仅本人 | 可查看本人发展流程 25 步详情；只读，不授 `develop:applicant:handle` |

## 5. 发展党员流程引擎设计

### 5.1 设计原则

**自定义状态机 + 规则策略**，不引入 Flowable/Activiti。理由：

1. 流程步骤固定（25 步来自中央组织部文件，极少变动），BPMN 的动态编排能力用不上
2. 党务规则是**领域规则**（1 年培养期、双过半票数），用 BPMN 表达需大量监听器硬编码
3. 表结构简单（4 张主表 vs `act_*` 30+ 张），统计看板（"各阶段人数分布"）一条 SQL 即可
4. 周期性考察（06/21 步每半年一次）在 BPMN 中需循环子流程，在状态机中天然是「多行记录」

### 5.2 表结构

```
dev_stage        阶段模板（5 条，静态）
   └ dev_step        步骤模板（25 条，静态：步骤码/所属阶段/办理角色/期限天数/材料清单/规则key）
        └ dev_step_record   步骤办理记录（动态，每人每步一行；周期性步骤多行）

dev_applicant    申请人实例（person_id + current_stage + current_step + status）
```

### 5.3 步骤的两类形态

| 类型 | 说明 | 步骤 | 落地方式 |
|---|---|---|---|
| **单次办理型** | 办理一次即流转下一步 | 除 06/21 外的 23 步 | `dev_step_record` 一行，`result` 决定流转方向 |
| **周期性考察型** | 按周期多次记录，满期后方可流转 | STEP_06（每半年）、STEP_21（预备期 1 年） | `dev_step_record` 多行，累计满足周期才允许推进 |

**为什么周期性步骤需要 `advance` 字段**：这两步同时受两条约束 ——「每半年记录一次」和「须满 1 年方可推进」。若把后者的期限校验套在每一次记录上，前几次考察记录都会被「未满 365 天」挡住，半年一次的考察**永远记不成**。因此办理表单用 `advance` 区分两种动作：

- `advance=false`（默认）：只记录一次考察，停留在本步骤，仅校验记录频率（`PERIODIC_RULE` 跳过 `INTERVAL_RULE`）
- `advance=true`：考察期满推进到下一步，此时才校验期限（`INTERVAL_RULE` 生效，`PERIODIC_RULE` 跳过）

**关于 `DEADLINE_RULE` 为何只警告不阻断**：党务工作中超期了事情仍然必须办。若硬性拦截，经办人会绕过系统线下处理，反而让系统数据失真。系统要做的是把超期情况如实暴露出来（记录 `is_overdue` 并在卡片上标红提醒）。这与 `INTERVAL_RULE` 不同 —— 培养教育不满 1 年属于**不可逾越的实体条件**，必须阻断。

### 5.4 规则策略（`DevStepRule` 接口）

```java
public interface DevStepRule {
    String ruleKey();                          // 与 dev_step.rule_key 对应
    RuleResult validate(DevContext ctx);       // 返回 通过 / 不通过 + 原因
}
```

| 规则 Key | 实现类 | 校验内容 | 阻断？ | 适用步骤 |
|---|---|---|---|---|
| `QUALIFICATION_RULE` | QualificationRule | 按步骤分派：申请入党年龄、培养联系人 1-2 名、入党介绍人 2 名、预审前须已确定为发展对象 | **阻断** | 01、05、09、13 |
| `DEADLINE_RULE` | DeadlineRule | 须在起算点后 N 天内办结 | **仅警告** | 02(30天)、17(90天)、24(90天) |
| `INTERVAL_RULE` | IntervalRule | 距基准步骤首次办结须满 N 天 | **阻断** | 06(距03满365天)、07(距03满365天) |
| `PERIODIC_RULE` | PeriodicRule | 周期性考察两次记录的最小间隔 | **阻断** | 06(180天)、21(90天) |
| `PROBATION_PERIOD_RULE` | ProbationPeriodRule | 须预备期满（读 `probation_end_date`，延长预备期后顺延） | **阻断** | 21、22 |
| `TRAINING_HOUR_RULE` | TrainingHourRule | 集中培训 ≥3 天**或** ≥24 学时（满足其一即可） | **阻断** | 11 |
| `VOTE_RULE` | VoteRule | 到会有表决权人数 > 应到人数的半数，**且** 赞成票 > 应到会有表决权的正式党员的半数 | **阻断** | 15、23 |
| `BRANCH_RULE` | BranchRule | 三出口：按期转正 / 延长预备期(6-12个月、仅 1 次) / 取消预备党员资格 | **阻断** | 23 |
| `MATERIAL_REQUIRED_RULE` | MaterialRequiredRule | 提示本步骤所需归档的材料 | **仅警告** | 除 19 外全部 |

> 上表与 `dev_step.rule_key` 的实际绑定一致，改流程前可用
> `SELECT step_code, rule_key FROM dev_step ORDER BY step_order;` 复核。

**两条"仅警告"规则是有意为之，不要改成阻断**：

- `DEADLINE_RULE` —— 党务工作中超期了事情仍然必须办。硬性拦截会逼经办人绕过系统线下处理，
  反而让数据失真。系统要做的是把超期如实暴露出来（记录 `is_overdue`、卡片标红）。
- `MATERIAL_REQUIRED_RULE` —— 材料补录在党务实践中很常见（纸质材料后补扫描件），
  硬拦会让历史材料无法补录。

**`PROBATION_PERIOD_RULE` 与 `INTERVAL_RULE` 的区别（重要）**：
`INTERVAL_RULE` 的基准是「基准步骤**首次办结**时间」—— 一个不可变的历史事实。
而延长预备期改变的是「什么时候算满期」这个**目标日期**，不是历史。
因此 STEP_21/22 用 `PROBATION_PERIOD_RULE` 读 `dev_applicant.probation_end_date`，
该字段在接收预备党员时置为「预备党员日期 + 1 年」，每次延长按月顺延。
**早期版本误用 `INTERVAL_RULE`，导致支部大会决定延长 6 个月后当事人第二天就能再次推进，
延长决定形同虚设。**

> 新增/调整步骤：改 `dev_step` 数据 + 必要时加一个策略类，**不改主流程代码**。

## 7. 配置约定

实际配置在 `hparty-server/hparty-admin/src/main/resources/application.yml`，关键项：

```yaml
server:
  port: 8080
  servlet:
    context-path: /api                # 所有接口都带 /api 前缀
spring:
  datasource:
    # 注意：characterEncoding 要填 Java 字符集名 UTF-8，填 MySQL 的 utf8mb4 会连不上库
    url: jdbc:mysql://127.0.0.1:3306/hparty?useUnicode=true&characterEncoding=UTF-8&connectionCollation=utf8mb4_general_ci&serverTimezone=Asia/Shanghai
    username: ${DB_USERNAME:root}
    password: ${DB_PASSWORD:123456}
  data:
    redis:
      host: ${REDIS_HOST:127.0.0.1}
      port: ${REDIS_PORT:6379}
sa-token:
  token-name: Authorization
  token-prefix: Bearer                # 前端发 "Authorization: Bearer <token>"
  timeout: 7200
hparty:
  captcha:
    enabled: true                     # 登录图形验证码开关
  file:
    storage: local                    # local | minio | oss（后两者未实现）
    local-path: D:/hparty/upload
    url-prefix: /api/file/preview
```

> `hparty.file.storage` 目前只实现了 `local`。切 OSS/MinIO 只需新增一个 `FileStorage`
> 实现类（接口在 `hparty-framework` 的 `file` 包），业务代码不用改。

> 生产环境配置见 `06-生产上线清单.md` 第 4 节。

## 9. 设计边界与后续演进

### 已确认的设计选择

| 事项 | 决定 | 说明 |
|---|---|---|
| 登录验证码 | **启用** | Redis 存 4 位字符，2 分钟过期；`hparty.captcha.enabled` 可关 |
| 多租户 | **不做** | 当前按**单棵党组织树**设计（一个党委及其下辖组织）。若将来要给多个互不相干的单位共用一套系统，需要引入 `tenant_id` 并改造数据权限，改动面较大 |
| 流程引擎 | **自定义状态机**，不用 BPMN | 理由见 5.1 |
| 文件存储 | **本地磁盘** | 抽象成 `FileStorage` 接口，可平滑切换 |

### 已知的设计边界（改动前请先读）

- **文件预览已改为受保护资源**：`/file/preview/**` 不在免登录白名单中，必须登录，并基于 `sys_file.org_id` 执行数据权限校验。前端通过 Axios 携带 `Authorization` 获取 Blob，再使用 object URL 打开；不得恢复为直接 `<img src=fileUrl>` / `<a href=fileUrl>` 的匿名访问模式。详见 `06-生产上线清单.md` 第 6 节。
- **`data_scope=5`（自定义范围）按 `sys_role_dept` 校验**；人员型资源按 ID 访问同时通过 `canAccessData(orgId, personId)` 处理 SELF/CUSTOM 等范围，避免列表权限与详情权限口径不一致。
- **`sys_dept.member_count` 是冗余列，不会随人员增减自动更新。**
- **字典缓存是单机 JVM 缓存**（`SysDictTypeService` 里的 `ConcurrentHashMap`），
  多实例部署需改 Redis。
